# Fresh NanoTrack V3 RK3566 Deployment Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Export, convert, implement, deploy, and verify a fresh NanoTrack V3 three-model RKNN tracker on the RK3566 board without using the old board project.

**Architecture:** The Linux server exports the author's V3 PyTorch model into fixed template-backbone, search-backbone, and head ONNX graphs, verifies them against PyTorch, and converts them with Rockchip RKNN-Toolkit2 v2.3.2. A new headless C++ application on the board links only platform OpenCV/RKNN dependencies, queries actual tensor metadata, runs the three graphs, performs official tracker post-processing, and writes video, CSV, and performance evidence.

**Tech Stack:** Python 3.10, PyTorch/ONNX/ONNX Runtime, RKNN-Toolkit2 2.3.2, C++14, CMake, OpenCV 4.10, RKNN Runtime 2.3.2, pytest/CTest, FFmpeg.

**Spec:** `docs/superpowers/specs/2026-09-29-nanotrack-v3-rk3566-design.md`

## Review Focus

- Freshly exported backbone channel counts or layouts differ from assumptions: reject metadata mismatches before inference and test layout conversion with literal tensors.
- A malformed or out-of-frame initial box could cause invalid crops: validate and fail before model execution.
- RKNN Runtime and kernel driver incompatibility could be hidden by ignored return codes: propagate every load/query/run error with versions.
- Empty/corrupt video or output-writer failure could produce a zero-byte artifact with exit zero: require decoded and tracked frames plus finalized outputs.
- Non-finite or extreme head outputs could corrupt tracker state: validate decoded values and clip every box to frame bounds.
